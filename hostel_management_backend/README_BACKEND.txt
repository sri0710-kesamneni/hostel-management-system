HOSTEL ROOM ALLOCATION AND MANAGEMENT SYSTEM — BACKEND STARTER
Stack: Java 25 (LTS), Maven, Jakarta Servlet 6, Tomcat 10.1+, Oracle JDBC, Gson.

IMPORTANT
This is a backend starter template. It assumes the Oracle column names in
database/hostel_schema_template.sql and ResourceConfig.java. Compare these with
your real Week 1 schema and edit ResourceConfig.java before running. Do not run
the template SQL against an existing schema without checking first.

as a sibling:
DBMS_project/
  pom.xml
  src/
  database/
  frontend/hostel_management_frontend/

DATABASE CONFIGURATION
Set environment variables in the same Windows terminal before starting Maven/Tomcat:
$env:HOSTEL_DB_URL="jdbc:oracle:thin:@//localhost:1521/XEPDB1"
$env:HOSTEL_DB_USER="YOUR_ORACLE_USERNAME"
$env:HOSTEL_DB_PASSWORD="YOUR_ORACLE_PASSWORD"

Replace XEPDB1 with your actual Oracle service name (for example, XE or XEPDB1 depending on your installation).
Do not commit credentials to Git or paste passwords into shared reports.

BUILD
Use Java 25 or newer to build and run the backend. The WAR targets Java 25 bytecode,
so Tomcat must also run on Java 25 or newer.
From the directory containing pom.xml:
mvn clean package
The output should be target/hostel-management.war.
Copy that WAR into Tomcat 10.1's webapps folder, then start Tomcat.
The API context path will normally be /hostel-management:
GET  http://localhost:8080/hostel-management/api/health
GET  http://localhost:8080/hostel-management/api/students
GET  http://localhost:8080/hostel-management/api/rooms
GET  http://localhost:8080/hostel-management/api/applications
GET  http://localhost:8080/hostel-management/api/allocations
GET  http://localhost:8080/hostel-management/api/payments

CRUD API
GET    /api/students             list records
GET    /api/students?id=123      get record by primary key
GET    /api/students?q=meera     simple text search
POST   /api/students             insert JSON
PUT    /api/students?id=123      update JSON fields
DELETE /api/students?id=123      delete by primary key
Equivalent endpoints exist for hostels, room-types, rooms, applications, allocations, payments.

Example POST JSON (adapt field names and IDs to your actual schema):
{
  "reg_no": "VIT2026001",
  "student_name": "Sample Student",
  "email": "sample@example.edu",
  "phone": "9876543210",
  "gender": "Other",
  "department": "Computer Science"
}
The primary key is generated by Oracle identity columns in the provided template. Do not include student_id in insert requests.

LOGIN
POST /api/login with JSON {"email":"...","password":"..."}.
The endpoint expects USERS.PASSWORD_HASH to be a BCrypt hash. It will not accept a plain-text password.
No admin user is seeded by this template. Create one using a trusted BCrypt hash-generation method before testing login.
POST /api/logout ends the session.

FRONTEND INTEGRATION
Your current app.js uses localStorage demo data. It will NOT automatically use this API yet.
Once the API is running, update js/app.js to use fetch() requests to the API endpoints. Since the frontend is served on a different port, configure a same-origin proxy or add narrowly scoped CORS configuration for your exact frontend origin. Do not use wildcard CORS with credentialed sessions.
Use credentials: "include" in fetch requests if relying on session cookies, and test preflight/OPTIONS behavior.
Always revalidate input/business rules on the backend; client-side checks are only for usability.

SECURITY / PRODUCTION NOTES
This is a college-project starter, not production-hardened. Protect CRUD endpoints with session/role checks before public deployment, implement CSRF protection for cookie-based sessions, use HTTPS for deployment, and apply transaction/locking logic for allocation capacity so simultaneous requests cannot overfill rooms.
